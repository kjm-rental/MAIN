## Implemented server endpoints

- `POST /api/paymongo/checkout`: authenticated Supabase cookie session, exact configured Origin required, JSON `{ "bookingId": "UUID", "idempotencyKey": "UUID" }`. Keep the same key on retries. Returns only status, intent ID and allowlisted hosted Checkout URL. Uses the locked quote and existing reservation via the foundation RPCs, never creates bookings. Only finalized confirmed test bookings are supported. New sessions require both the environment feature flag and database readiness gate.
- `POST /api/paymongo/webhook`: raw-body HMAC-SHA256 verification using the test signature and five-minute timestamp window; rejects live events. Subscribe to `checkout_session.payment.paid`. Retrieves session/payment data from PayMongo before settlement. Event identity/body hash is marked complete only after atomic settlement; simultaneous duplicate delivery is safe through settlement idempotency. Failed processing remains retryable. No raw payloads, credentials or provider errors are logged/returned.
- `POST /api/paymongo/reconcile`: `Authorization: Bearer <PAYMONGO_RECONCILIATION_SECRET>`. JSON `{ "after": null }` starts a five-intent cursor batch. Follow returned `nextCursor` until null, then restart the scan on the next scheduled run. Each result may be `pending`, `paid`, `review_required`, `expired_unpaid`, `creation_unresolved`, or `retry_required`. Alert on the last three review/failure states and retry failed IDs directly. Includes settled intents so delayed duplicates/refunds/disputes are detected and reported for review rather than silently credited. Nothing contributes to real cash ledgers or handover eligibility.

Configure a scheduler every 1–5 minutes; serialize full sweeps and allow up to 60 seconds per batch. Do not store the bearer token in URLs. Webhooks and reconciliation may drain existing transactions while the new-creation environment flag is off, but still require valid test-only server configuration. Existing reservations/expiry rules remain authoritative: cancellation or the local 30-minute deadline causes the hosted session to expire on reconciliation. Retrieve again after expiration to catch payment races. Late verified payments go to the foundation's review state; no reservation is revived or auto-confirmed.

## Interrupted creation

There is exactly one external creation POST per intent. No provider idempotency behavior is assumed. A crash, rejected POST, or ambiguous network outcome consumes the durable claim permanently. Repeating checkout does not issue another POST. If its hosted session ID is known from the PayMongo test dashboard, recover with authorized reconciliation JSON `{ "checkoutId": "UUID", "sessionId": "cs_..." }`; the server retrieves and validates test mode, reference and amount before attaching it. A correctly signed paid webhook can also recover the attachment using the durable reference UUID. If no session ID can be recovered, the exact blocker is unknown provider creation outcome; investigate with PayMongo. Do not clear the claim or create a replacement session. `reference_number` alone is not assumed to provide automatic lookup or idempotency.

Multiple paid payments, refunds, disputes, mismatched mode/amount/reference/session, and malformed provider responses are rejected for review. This stage does not perform refunds, alter bookings, release reservations, or modify cash records. Review errors appear as `retry_required` to the scheduler; operational alerting is still required. Cash flows for bookings without a test checkout are unchanged.
